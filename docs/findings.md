# Findings

Spec claims checked against running software.

Results come from OPA 1.22.4 and OpenFGA v1.22.1 (`OPENFGA_EXPERIMENTALS=authzen`), and are pinned by `tests/test_findings.py` and `tests/test_common.py`.

| # | Spec claim | Result | Evidence |
|---|---|---|---|
| F1 | OpenFGA returns an error, not a deny, when a condition parameter is missing ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified.** HTTP 400 `validation_error`, "tuple '…' is missing context parameters '[resource_owner]'". Without the always-pass rule, missing and legacy tasks would give 503. With the shim, both give `decision: false` (golden `get-missing`, `get-legacy-no-owner`; smoke: 404 end to end). | `test_openfga_missing_condition_parameter_is_an_error` |
| F2 | `subject.id` is not in OpenFGA's condition context, only `subject_*` properties ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified.** A request with `subject.id` but without `properties.id` fails with "missing … '[subject_id]'". | `test_openfga_subject_id_is_not_in_condition_context` |
| F3 | OpenFGA ID pattern/length limits **[unverified]**; "the shim hashes long IDs" ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified, and stricter than the spec assumes.** Subject IDs must match `^[^:#@\s]{1,500}$` and resource IDs `^[^:#@\s]{1,256}$`. Length isn't the main problem: every `<iss>\|<sub>` owner (has `:`) and every LS Login `sub` (`…@lifescience-ri.eu`, has `@`) is rejected. The shim must hash or encode every subject ID, not only long ones. Ours hashes all of them and passes the real ID as `subject_id`. **Spec text to change:** "the shim hashes long IDs" → "the shim encodes every subject ID (OpenFGA rejects `:`, `#`, `@`, whitespace)". | `test_openfga_identifier_limits` (6 cases), boundaries at 500/256 |
| F4 | Prefix tests need expansion in engines without quantifiers; reference prefixes must end in a delimiter, or expansion and `startswith` disagree ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified.** Expansion equals `startswith` for `:`-terminated prefixes on every golden entitlement set; `urn:g:vo` vs `urn:g:vo2#x` disagrees. **Addition:** OpenFGA's CEL conditions support `exists`/`all` and `startsWith`, so OpenFGA needs no expansion and tests prefixes natively, but only within its CEL cost budget: with the default `OPENFGA_MAX_CONDITION_EVALUATION_COST`, a condition over more than about 5 entitlements or executors fails with HTTP 400 ("cost limit exceeded"), so ordinary LS Login users with dozens of entitlements would get 503 (measured in the service review; the result also depends on list order, because `exists` short-circuits). Compose raises the budget to 100000, the shim caps lists at `SHIM_MAX_LIST_ITEMS` (1024; above that it answers 502), and golden cases at 1024 items pin it. The cost grows with list length × configured values and prefixes × string length (the round-2 review saw 8 VOs fail at 1024 entitlements). So the setup job runs a self-check: worst-case requests at `SHIM_MAX_LIST_ITEMS` items of 200 characters for every configured service. It exits non-zero, so the shim doesn't start, if OpenFGA errors. Checked: with a budget of 2000, setup fails with "actual cost limit exceeded". Separately, OpenFGA's gRPC gateway rejects requests over about 602 KiB, so the OpenFGA shim accepts at most 512 KiB (`SHIM_MAX_BODY_BYTES`). Expansion stays in `common` for Cedar and Casbin. | `test_prefix_expansion_*`; the OpenFGA model's `entitled` condition |
| F5 | In OpenFGA's AuthZEN, `action.name` must be a relation ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified.** An unknown action gives 400 (it would be a 503 at the TES). The shim validates action names first and denies. | `test_openfga_unknown_relation_is_an_error` |
| F6 | Native AuthZEN PDPs return only `decision` ([§3.5](specification.md#35-list-filtering)) | **Verified** for OpenFGA: the body is exactly `{"decision": …}`. | `test_openfga_answers_decision_only` |
| F7 | `tes_task_set:own/all` work natively in OpenFGA with `user:*` tuples; `tes_task` needs the `tes_service` rewrite with a conditioned `user:*` tuple ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified** by the full golden replay. Design note: OpenFGA allows only one tuple per (object, relation, user), so owner and admin needed separate relations (`owner`, `admin`, with `GetTask: owner or admin`). Since [#23](https://github.com/elixir-cloud-aai/tes-authz/issues/23) the model is owner only: no `admin` relation, and no tuples on `all`, which is therefore denied. | `test_golden_decision[openfga-*]` |
| F8 | OPA needs a ~50-line shim ([§7](specification.md#7-reference-decision-service-and-engines)) | **Verified.** The front is ~60 lines with docstrings. The Rego policy also enforces the contract, so OPA called directly (Data API) gives the same decision for every golden request. | `test_golden_decision[opa-data-api-*]` |
| F9 | OpenFGA's AuthZEN endpoint is store-scoped, so v1 config takes the full URL ([§2](specification.md#2-standards-considered), [§7](specification.md#7-reference-decision-service-and-engines)) | **Verified**: `/stores/{id}/access/v1/evaluation`. The shim hides this, so the TES config holds the shim URL. | `fga_eval` fixture |
| F10 | `X-Request-ID` (AuthZEN §10.1.3) | OpenFGA **doesn't echo** a client-supplied ID; both shims do, for log correlation. | `test_openfga_does_not_echo_request_id`, `test_shims_echo_request_id` |
| F11 | (not in the spec) shim robustness | Lone UTF-16 surrogates are denied by the contract check (Go would map them to U+FFFD, so distinct IDs could compare equal in OPA); identifiers with a trailing newline are hashed; requests without `Content-Length` get 411; a socket read idle for 5 s drops the client. Total request time and the number of connections aren't bounded by the shims; the mesh in front of them must do that. Empty prefixes in the policy data are rejected at setup, because `"".startsWith("")` would let the shim's empty-image sentinel pass. | `test_shims_deny_lone_surrogates`, `test_shims_deny_service_id_with_newline`, `test_shims_require_content_length`, `test_openfga_shim_rejects_lists_over_limit` |
| F12 | (not in the spec) service clients in OpenFGA tuple context | OpenFGA refuses tuples whose condition context strings hold control characters, and also some non-ASCII ones (HTTP 400, "contains forbidden characters"; checked: newline, tab, DEL, U+0085 and `é` refused, a space accepted). So the `listed_client` tuple joins each listed pair as `"<iss> <client_id>"` with one space, and both engines accept only printable ASCII without spaces (`!` to `~`) in both values, which keeps the pair unambiguous; OPA refuses the same data, so both engines decide alike. | `test_openfga_refuses_control_characters_in_tuple_context` |

Not checked here: Cedar entity tags, Cerbos role mapping and Topaz directory behaviour (not in phase 1); OpenFGA Search paging (Search isn't used); Passport validation.

See also the [owner rule](operators.md#owner-rule).
